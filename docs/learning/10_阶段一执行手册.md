## 0. 阶段一的验收标准（做完的判据）

阶段一不是一个"模块写完"的阶段，而是一个**能真实跑起来的业务场景**。

### 0.1 分两段验收（★ 2026-09-16 调整：CMPP 后置）

```text
【第一段 · 接口闭环（验收点 A）】—— 不碰 CMPP，用 HTTP 接口 + 队列观察即可验收
客户 POST /sms/single_send
  → beacon-api 校验链（apikey → ip → sign → template）
  → MQ sms_pre_send_topic          ← 观察点 1：队列出现消息
  → beacon-strategy 策略链（本阶段只做 route 一段）
  → MQ sms_gateway_topic_{channelId} ← 观察点 2：消息被路由到正确队列
  → beacon-smsgateway（stub：只消费 + 打印日志，不发 CMPP） ← 观察点 3：日志出现完整报文摘要
```

**验收点 A（Interface 闭环）**：用 Postman/curl 发一条 → api 返回 `{code:0,uid,sid}` → RabbitMQ 管理台看到两级队列流转 → smsgateway 日志打印出待下发的报文摘要。

```text
【第二段 · CMPP 真下发（验收点 B）】—— 阶段一收尾
beacon-smsgateway 换成真实现（Netty + CMPP 2.0）
  → CMPP 模拟器收到 Submit，回 SubmitResp
  → 网关日志出现应答
```

**验收点 B（CMPP 真下发）**：`CMPP 模拟器收到 Submit，日志有应答`。

> **为什么要分段**：验收点 A 只需要 **Nacos + RabbitMQ**，不需要 CMPP 模拟器、也不需要调试二进制协议 —— 能尽早拿到"接口能受理、策略能路由、网关能消费"的反馈。协议层的排错成本高（字节错位、编码、鉴权时间戳），留到最后单独攻。

**明确不做**（留给后续阶段，本阶段不要提前实现）：

| 不做的事 | 归属阶段 |
| --- | --- |
| 真实扣费 / 余额拦截（fee 过滤器） | 阶段二 |
| 限流（limitOneHour）、权重路由完整版 | 阶段三 |
| ES 写日志 / 回执状态更新（search） | 阶段四 |
| 客户回调推送（push） | 阶段五 |
| 后台登录 / 前端（webmaster · frontend） | 阶段六 |
| 监控巡检（monitor） | 阶段七 |
| 批量提交 / 模板 / 签名审核 / 黑名单完整版 | 阶段八 |

**本阶段并入的缺陷规避项**（`09` §4.5 指定）：🟡#23（缓存签名不覆盖 body/query）→ 第 11 步；🔴#25（内部 token 默认空）→ 第 12 步；🔴#7（策略链 fail-open / 链序）与 🔴#12（敏感词树）留到阶段三/八完整版，本阶段只保证"留出设计位置、不让旧缺陷复现"。

## 13. 第 11 步 · `CacheAuthSignUtil` + `CacheAuthHeaders` + 单测（★ 修 🟡#23）

- **文件**：`beacon-common/.../security/CacheAuthSignUtil.java`、`CacheAuthHeaders.java` + 单测。
- **这是本阶段唯一"主动修缺陷"的一步，必须做对**：
  1. 旧版签名 payload = `caller + "\n" + timestamp + "\n" + method + "\n" + path` —— **不覆盖 body/query 值**，写接口内容可被篡改而不破坏验签（🟡#23）。重写版 **payload 必须包含 body 摘要与规范化 query**。
  2. 加入 **nonce**（防 300s 窗口内重放）。
  3. 验签用 **恒时比较**（`MessageDigest.isEqual`），**禁止** `String.equals`。
  4. `CacheAuthHeaders` 集中声明头名（`X-Cache-Caller` / `X-Cache-Timestamp` / `X-Cache-Sign` / nonce），**禁止散落字符串**。
  5. **服务端与客户端的 path 口径必须一致** —— 旧版服务端用 `request.getRequestURI()`、客户端用 `template.path()`，经网关/contextPath 即验签失败（旧报告 R8）。重写版定义**唯一的规范化 path 函数**，两边共用。
- **单测（必写）**：
  - 相同入参 → 相同签名（确定性）；
  - **改动 body 任意一个字符 → 签名变化**（这条单测就是 🟡#23 的回归防线）；
  - 改动 query → 签名变化；
  - nonce 不同 → 签名不同；
  - 恒时比较对不等长输入不抛异常。
- **学习点**：HMAC payload 设计 —— 为什么"分隔符 + 字段顺序"本身是协议的一部分。
- **验收**：`mvn -q -pl beacon-common -am install`（含单测）通过。
- **commit**：`feat: 阶段一第11步 新增缓存签名工具签名覆盖body与query`

  - `netty/NettyClient`：EventLoopGroup **复用不泄漏**（修 P15）；重连**不在 I/O 线程阻塞**（修 P16）；`channel` 字段 **volatile**（修 P22）
  - `netty/NettyStartCMPP`：**异步启动，不在 `initMethod` 里 `connect().sync()`**（修 P17 —— CMPP 不可达时应用仍能启动）
  - `netty/CMPPDecoder` / `CMPPEncoder`（本步只处理 Connect 系命令）
  - `netty/HeartHandler` + `IdleStateHandler`：心跳**必须校验 ActiveTestResp 应答**（修 P18），**回显 sequenceId**
- **必须写对的协议点**（`docs/protocol/01` §3、§6；P5~P7、P21、P22）：
  - Connect：`SourceAddr`(6) + `AuthenticatorSource`(16，MD5 字节级拼接) + `Version`(**`0x20`**，不是 1) + `Timestamp`(**24 小时制 `MMddHHmmss`**)
  - **必须校验 ConnectResp 的 `Status`**（`!=0` 视为连接失败并记录原因）
  - 短帧防御：声明长度 0~3 时**不得抛 `ArrayIndexOutOfBoundsException`**（修 P21，用帧切片解析而非原地改写，顺带修 P10）
- **测试（关键，不需模拟器）**：`EmbeddedChannel` 单向测
  - 编码 Connect 后**字节数 = 39**，且偏移 6~21 是 MD5、偏移 22 是 `0x20`
  - 解码一段已知 ConnectResp 字节流
  - 解码长度声明为 0/2 的畸形帧 → **不抛异常、通道不关闭**
- **学习点**：Netty pipeline 的入站/出站方向（为什么编码器写在解码器前面）；`LengthFieldBasedFrameDecoder` 各参数含义。
- **验收**：`mvn -q -pl beacon-smsgateway -am install` 通过；启动 gateway 后日志出现"与 CMPP 服务端握手成功（Status=0）"。
- **commit**：`feat: 阶段一第16步 新增CMPP连接与Connect握手`

## 19. 第 17 步 · CMPP 业务层：Submit 编码 + 下发 + SubmitResp

- **交付物**：
  - `entity/CmppSubmit`、`CmppSubmitResp`
  - `SmsGatewayListener` 接上真 `SmsSender`：把 `StandardSubmit` → `CmppSubmit`，**检查 `submit()` 返回值**（修 P24）
  - `entity/CmppDeliver` + `DeliverRunnable` 的**框架位**（回执链本阶段不验收，阶段四接 search）
  - 收 `Deliver` 时**必须回 `Deliver_Resp`**（修 P8），即使本阶段不处理回执业务
- **必须写对的协议点**（`docs/protocol/01` §4；P2~P4、P9、P11~P13）：
  - `Msg_Fmt` 字段**必须存在且位置正确**（旧版整体错位 1 字节 —— P2，本步最大的坑）
  - `Msg_Id` **平台生成、非 0**（P3）；`SubmitResp` 的 `Msg_Id` 保留原始 8 字节，**不做 `Math.abs`**（P9）
  - `srcId` / `Msg_src` **来自通道配置**（P13，旧版硬编码追加 `"1630"`）
  - `Pk_total` / `Pk_number` / `TP_udhi` 的字段位（本阶段单条短信可先不分片，但**字段必须写对位置**）
  - 状态报告字段**固定 ASCII，不按 `Msg_Fmt` 切换字符集**（P11）
- **测试（不需模拟器）**：`EmbeddedChannel` + 逐字段偏移断言
  - 编码后 `Msg_Fmt` 位于协议规定偏移且值正确（P2 回归防线）
  - `Msg_Id != 0`
  - `SubmitResp` 解码后 `Msg_Id` 与发送时报文一致、`Result` 正确映射到 `CMPP2ResultEnums`
- **学习点**：CMPP 定长字段的补位规则；为什么"字段错位 1 字节"这类缺陷编译期完全发现不了。
- **验收**：`mvn -q -pl beacon-smsgateway -am install` 通过；有模拟器后单发一条 → 模拟器打印收到 Submit 且字段可解。
- **commit**：`feat: 阶段一第17步 新增CMPP Submit编码下发与SubmitResp处理`

## 20. 第 18 步 · 网关可靠性：状态暂存 + 线程池 + 超时兜底

- **交付物**：
  - `CmppStateStore`：`cmpp:submit:{seq}`（TTL 600s）暂存中间状态（走 beacon-cache）
  - `config/ThreadPoolConfig`：标准 `ThreadPoolExecutor`，Bean 名 `cmppSubmitPool` / `cmppDeliverPool` **固定不变**；显式容量 + `CallerRunsPolicy`（修 P35/P47，替代 hippo4j）
  - `SubmitRepoRunnable`：处理 SubmitResp，按 sequenceId **原子取回**暂存（pop 语义吸收重复应答）
  - **超时兜底任务**：扫描超过 TTL 仍未收到 SubmitResp 的 submit → 置失败 + 告警（修 P25，旧版短信永久 waiting）
  - **SubmitResp 失败也要触发客户回调**（修 P26，本阶段可只留框架位）
  - 缓存调用异常**显式捕获**，不得让后续步骤被静默跳过（修 P27）
- **学习点**：为什么中间状态要外置 Redis 而不是进程内 Map（网关重启 / 多实例）；`CallerRunsPolicy` 为什么比 `AbortPolicy` 更适合回执风暴场景。
- **验收**：`mvn -q -pl beacon-smsgateway -am install` 通过；构造"模拟器不回 SubmitResp"场景 → TTL 后状态被置失败且有日志。
- **commit**：`feat: 阶段一第18步 新增网关状态暂存线程池与超时兜底`

## 附录 B · CMPP 模拟器缺失时的最小替代方案

若 `模拟cmpp-server.zip` 找不到，用一个最小 Netty 服务端顶替（只实现阶段一需要的 3 个命令）：

1. 监听 `127.0.0.1:7890`，pipeline：`LengthFieldBasedFrameDecoder` + 自写 Decoder/Encoder。
2. 收 `CMPP_CONNECT (0x00000001)` → 校验 `AuthenticatorSource`（可先放宽）→ 回 `CONNECT_RESP (0x80000001)`，`Status=0`。
3. 收 `CMPP_SUBMIT (0x00000004)` → **打印收到的 Msg_Id / Msg_Fmt / 内容**（这就是验收证据）→ 回 `SUBMIT_RESP (0x80000004)`，`Msg_Id` 回显、`Result=0`。
4. 收 `CMPP_ACTIVE_TEST (0x00000008)` → 回 `ACTIVE_TEST_RESP (0x80000008)`，**回显 sequenceId**。
5. 可选：延时几秒主动发 `CMPP_DELIVER (0x00000005)` 状态报告（`Stat="DELIVRD"`）—— 本阶段不验收回执链，可跳过。
6. 该模拟器**不入本仓库**（属测试工具），放仓库外或 `_reference/` 旁独立目录。
