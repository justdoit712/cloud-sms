## 0. 阶段一的验收标准（做完的判据）

阶段一不是一个"模块写完"的阶段，而是一个**能真实跑起来的业务场景**：

```text
客户 POST /sms/single_send
  → beacon-api 校验链（apikey → ip → sign → template）
  → MQ sms_pre_send_topic
  → beacon-strategy 策略链（本阶段只做 route 一段，够跑通即停）
  → MQ sms_gateway_topic_{channelId}
  → beacon-smsgateway CMPP Submit（Netty）
  → CMPP 模拟器收到 Submit 并回 SubmitResp
  → 网关日志出现应答，短信状态不再是 waiting
```

**验收动作（唯一的、必须真的跑起来）**：`CMPP 模拟器收到 Submit，日志有应答`。

**明确不做**（留给后续阶段，本阶段不要提前实现）：

| 不做的事 | 归属阶段 |
| --- | --- |
| 真实扣费 / 余额拦截（fee 过滤器） | 阶段二 |
| 限流（limitOneHour）、权重路由完整版 | 阶段三 |
| ES 写日志 / 回执状态更新（search） | 阶段四 |
| 客户回调推送（push） | 阶段五 |
| 后台登录 / 前端（webmaster · frontend） | 阶段六 |
| 监控巡检（monitor） | 阶段七 |
| 批量提交 / 模板 / 签名审核 / 黑名单完整版 | 阶段八 |

**本阶段并入的缺陷规避项**（`09` §4.5 指定）：🟡#23（缓存签名不覆盖 body/query）→ 第 11 步；🔴#25（内部 token 默认空）→ 第 12 步；🔴#7（策略链 fail-open / 链序）与 🔴#12（敏感词树）留到阶段三/八完整版，本阶段只保证"留出设计位置、不让旧缺陷复现"。

### 1.1 中间件到位的最晚时点（关键排期约束）

**第 1~11 步全部不需要中间件**，可以一路写下去、一路编译+跑单测。**第 12 步开始必须有 Nacos + RabbitMQ**。

```text
第 1~11 步  ──────────────  纯代码，可离线推进（编译 + 单测）
                 ↓ 最晚在此前完成 0-a / 0-b

第 13~15 步     ──────────  需要 Nacos + RabbitMQ + Redis + CMPP 模拟器
```

> **推论**：中间件没装不妨碍现在开工；但若想在第 15 步一次通过，0-a~0-c 应在第 12 步之前完成。

## 8. 第 6 步 · `ExceptionEnums` + 单测

- **文件**：`beacon-common/.../enums/ExceptionEnums.java` + `src/test/java/.../enums/ExceptionEnumsTest.java`
- **本阶段最小集**（只要求用到的；后续步骤按需追加）：参数错误、apikey 无效、IP 不允许、签名无效、模板不匹配、手机号格式错误、余额不足、无可用通道、内部令牌无效、未知错误。
- **必须修掉的旧缺陷**：
  1. **code 重复**：旧版 `UNKNOWN_ERROR` 与 `KAPACHA_ERROR` 都是 `-100`。重写版**全表 code 唯一**，由单测断言。
  2. **拼写**：`KAPACHA` → `CAPTCHA`。
  3. **文案**：`BALANCE_NOT_ENOUGH` 旧文案"手客户余额不足"多字 → 改对。
  4. **枚举名**：`UNKNOW` → `UNKNOWN`。
- **枚举形态**：`record` 化不可变元数据（code + msg），或用 `sealed`；**枚举本身用 enum + final 字段**（枚举不能是 record），提供 `getMsg()`。
- **单测（必写）**：
  - 遍历全部枚举值，断言 **code 两两不重复**（用 `Set` 收集 size 校验）—— 这条单测是防止旧缺陷复发的关键。
  - 断言每个 msg **非 null 且非空白**（`isBlank()`）。
- **学习点**：错误码表设计 —— 为什么"业务码区段划分"（外部业务 / 后台 / 缓存同步）比连续编号更重要。
- **验收**：`mvn -q -pl beacon-common -am install`（含单测）通过。
- **commit**：`feat: 阶段一第6步 新增ExceptionEnums错误码表并修复重复码`

## 13. 第 11 步 · `CacheAuthSignUtil` + `CacheAuthHeaders` + 单测（★ 修 🟡#23）

- **文件**：`beacon-common/.../security/CacheAuthSignUtil.java`、`CacheAuthHeaders.java` + 单测。
- **这是本阶段唯一"主动修缺陷"的一步，必须做对**：
  1. 旧版签名 payload = `caller + "\n" + timestamp + "\n" + method + "\n" + path` —— **不覆盖 body/query 值**，写接口内容可被篡改而不破坏验签（🟡#23）。重写版 **payload 必须包含 body 摘要与规范化 query**。
  2. 加入 **nonce**（防 300s 窗口内重放）。
  3. 验签用 **恒时比较**（`MessageDigest.isEqual`），**禁止** `String.equals`。
  4. `CacheAuthHeaders` 集中声明头名（`X-Cache-Caller` / `X-Cache-Timestamp` / `X-Cache-Sign` / nonce），**禁止散落字符串**。
  5. **服务端与客户端的 path 口径必须一致** —— 旧版服务端用 `request.getRequestURI()`、客户端用 `template.path()`，经网关/contextPath 即验签失败（旧报告 R8）。重写版定义**唯一的规范化 path 函数**，两边共用。
- **单测（必写）**：
  - 相同入参 → 相同签名（确定性）；
  - **改动 body 任意一个字符 → 签名变化**（这条单测就是 🟡#23 的回归防线）；
  - 改动 query → 签名变化；
  - nonce 不同 → 签名不同；
  - 恒时比较对不等长输入不抛异常。
- **学习点**：HMAC payload 设计 —— 为什么"分隔符 + 字段顺序"本身是协议的一部分。
- **验收**：`mvn -q -pl beacon-common -am install`（含单测）通过。
- **commit**：`feat: 阶段一第11步 新增缓存签名工具签名覆盖body与query`

> **至此 common 模块的"场景一最小集"完成，且全部有单测、全程未依赖中间件。**

## 附录 B · CMPP 模拟器缺失时的最小替代方案

若 `模拟cmpp-server.zip` 找不到，用一个最小 Netty 服务端顶替（只实现阶段一需要的 3 个命令）：

1. 监听 `127.0.0.1:7890`，pipeline：`LengthFieldBasedFrameDecoder` + 自写 Decoder/Encoder。
2. 收 `CMPP_CONNECT (0x00000001)` → 校验 `AuthenticatorSource`（可先放宽）→ 回 `CONNECT_RESP (0x80000001)`，`Status=0`。
3. 收 `CMPP_SUBMIT (0x00000004)` → **打印收到的 Msg_Id / Msg_Fmt / 内容**（这就是验收证据）→ 回 `SUBMIT_RESP (0x80000004)`，`Msg_Id` 回显、`Result=0`。
4. 收 `CMPP_ACTIVE_TEST (0x00000008)` → 回 `ACTIVE_TEST_RESP (0x80000008)`，**回显 sequenceId**。
5. 可选：延时几秒主动发 `CMPP_DELIVER (0x00000005)` 状态报告（`Stat="DELIVRD"`）—— 本阶段不验收回执链，可跳过。
6. 该模拟器**不入本仓库**（属测试工具），放仓库外或 `_reference/` 旁独立目录。
