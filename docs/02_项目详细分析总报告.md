## 1. 项目定位与背景

`beacon-cloud`（GitHub: justdoit712/beacon-cloud）是一个基于 Spring Cloud 的**短信平台（SP 短信服务商平台）**，覆盖短信业务的完整闭环：

```
客户系统 → 接入受理 → 策略过滤 → 通道路由 → 运营商网关(CMPP) → 状态回执 → 客户回调
                                              └→ 日志入 ES → 后台检索/统计
```

**业务参与方：**

| 参与方 | 说明 |
| --- | --- |
| 客户系统 | 通过 apikey 调用 `beacon-api` 提交短信发送请求，接收状态回调 |
| 平台服务 | `beacon-api` / `beacon-strategy` / `beacon-smsgateway` / `beacon-search` / `beacon-push` |
| 运营后台 | `beacon-webmaster`（管理客户、通道、策略、模板、敏感词、黑名单等） |
| 基础设施 | Nacos、MySQL、Redis、RabbitMQ、Elasticsearch、XXL-Job、CMPP 服务端（模拟器） |

仓库根目录还包含：`模拟cmpp-server.zip`（本地 CMPP 模拟服务端）、`containers.json` + `docker_backup.tar.gz`（阿里云服务器上 mysql/es 容器迁移备份）、`walkthrough.md`（容器迁移指南）、`xxl-job/jobhandler`（线上 job 执行日志）。

## 3. 架构总览

### 3.1 微服务划分（9 模块）

```text
                    ┌──────────────┐     内部接口(JWT + token)
 客户系统 ──HTTP───▶ │  beacon-api  │◀───────────────────── beacon-webmaster (运营后台, Shiro+JWT+MyBatis)
                    └──────┬───────┘                                  │
                           │ sms_pre_send_topic                       │ Feign/HTTP
                           ▼                                          ▼
                    ┌──────────────┐                          ┌──────────────┐
                    │beacon-strategy│◀──── 策略链/路由缓存 ────│ beacon-cache  │ (统一 Redis 服务, 签名鉴权)
                    └──────┬───────┘                          └──────────────┘
                           │ sms_gateway_topic_{channelId}          ▲
                           ▼                                        │
                    ┌──────────────┐   CMPP over TCP(Netty)  ┌──────┴───────┐
                    │beacon-smsgateway│◀────────────────────▶│ CMPP 服务端   │
                    └──┬────┬────┬──┘  (运营商/模拟器)        └──────────────┘
        sms_write_log  │    │    └─── sms_push_report_topic ──▶ beacon-push ──HTTP──▶ 客户回调URL
                       │    └──────── sms_gateway_normal_exchange ──(TTL 10s)──▶ dead_queue ─▶ beacon-search (更新状态)
                       ▼
                beacon-search ──ES──▶ 日志/统计 (sms_submit_log_{year})

        beacon-monitor (XXL-Job): 队列积压巡检 + 客户余额巡检 → 邮件告警
```

### 3.2 分层理解

| 层 | 模块 |
| --- | --- |
| 接入层 | beacon-api、beacon-webmaster |
| 策略层 | beacon-strategy |
| 网关层 | beacon-smsgateway |
| 日志/回调层 | beacon-search、beacon-push |
| 平台支撑层 | beacon-common、beacon-cache、beacon-monitor |

### 3.3 架构特征

- **事件驱动**：主链路全部通过 RabbitMQ 队列解耦，消息体为 Jackson JSON 序列化的 `StandardSubmit` / `StandardReport`。
- **配置驱动**：API 校验链、策略链顺序均由 Nacos 配置（`filters=...` / Redis `clientFilters`）决定，过滤器以 `@Service("name")` 注入 Map 后按名查找。
- **缓存统一入口**：所有模块不直连 Redis，统一通过 `beacon-cache` 的 HTTP/Feign 接口（带 HMAC 签名鉴权 + 调用方权限模型）。
- **人工 ACK**：所有 MQ 消费者手动 `basicAck`，失败也 ACK（消费失败不重试、策略失败直接 ACK 丢弃），可靠性依赖业务侧补偿（写日志 + 推送失败报告）。
- **按年分索引**：ES 日志按 `sms_submit_log_{当前年}` 路由。

### 4.3 关系

## 5. RabbitMQ 消息拓扑

常量集中定义于 `beacon-common/.../constant/RabbitMQConstants.java`。

### 5.1 队列/交换机清单

| 名称 | 类型 | 声明位置 | 生产者 | 消费者 | 用途 |
| --- | --- | --- | --- | --- | --- |
| sms_pre_send_topic | Queue（durable） | beacon-strategy 与 beacon-api 双声明 | beacon-api | beacon-strategy PreSendListener | 预发送队列 |
| sms_gateway_topic_{channelId} | Queue（durable，动态 declare） | 路由时 `amqpAdmin.declareQueue` / monitor 任务 | beacon-strategy RouteStrategyFilter | beacon-smsgateway（`gateway.sendtopic`） | 按通道路由队列 |
| sms_write_log_topic | Queue | beacon-strategy | 策略/网关 | beacon-search SmsWriteLogListener | 写发送日志入 ES |
| sms_push_report_topic | Queue | beacon-strategy | 策略/网关 | beacon-push PushReportListener | 状态报告回调 |
| sms_gateway_normal_exchange / sms_gateway_normal_queue | Exchange+Queue（TTL 10s，绑定死信） | beacon-search 与 beacon-smsgateway **双模块重复声明** | beacon-smsgateway | （10 秒后转入死信） | 状态更新延迟中转 |
| sms_gateway_dead_exchange / sms_gateway_dead_queue | Exchange+Queue | 同上双声明 | normal 队列死信路由 | beacon-search SmsUpdateLogListener | 更新 ES 回执状态 |
| DELAYED_EXCHANGE / DELAYED_QUEUE | x-delayed-message | beacon-push | beacon-push 自身重投 | beacon-push delayedConsume | 回调失败延迟重试 |
| mobile_area_operator_topic | Queue | beacon-strategy | （号段/归属地同步，暂未接入消费者） | — | 预留 |

### 5.2 两个“延迟”机制（易混淆点）

1. **状态更新延迟**：网关把 `StandardReport` 发到 normal 交换机，normal 队列绑定 TTL（约 10s）+ 死信交换机，消息过期后进入 dead_queue，由 `beacon-search` 更新 ES 状态。目的是等「写日志」先完成，避免更新比写入早。
2. **回调重试延迟**：`beacon-push` 用 `x-delayed-message` 插件交换机实现，重试间隔序列 `{0, 15s, 30s, 60s, 300s}`，最多 5 次，客户回调须返回字符串 `"SUCCESS"` 才算成功。

### 5.3 消费确认策略

所有监听器手动 ACK。注意：`PreSendListener` 对 `StrategyException` 也直接 ACK（策略拒绝的消息不重试，直接丢弃），失败补偿依赖各过滤器内部先写日志/推送失败报告再抛异常。

## 6. Redis 缓存设计

`beacon-cache` 是唯一 Redis 访问入口，所有业务模块通过 Feign/HTTP 调用它（不直接连 Redis）。

### 6.1 缓存键约定（CacheKeyConstants）

| 前缀 | 内容 | 类型 |
| --- | --- | --- |
| client_business:{apiKey} | 客户业务配置（含 callbackUrl、isCallback、id） | Hash |
| client_sign: | 客户签名 | |
| client_template: | 客户模板 | |
| client_balance: | 客户余额镜像 | |
| client_channel:{clientId} | 客户-通道绑定（含权重、可用状态） | |
| channel:{channelId} | 通道详情（通道号、支持运营商、可用状态） | |
| phase: | 号段（手机号前缀→运营商/归属地） | |
| dirty_word | 敏感词库 | Set |
| black: | 黑名单 | |
| transfer:{mobile} | 携号转网结果 | |
| limit:minutes:/hours:/days: | 分钟/小时/天级限流 | |
| cmpp:submit:{seq} | 网关暂存待 SubmitResp 关联上下文（TTL 600s） | String(JSON) |
| cmpp:deliver:{msgId} | 网关暂存待状态报告关联上下文（TTL 86400s） | String(JSON) |

（统一命名空间前缀，如 `beacon:dev:beacon-cloud:cz:`，由 NamespaceKeyResolver 控制。）

### 6.2 beacon-cache 鉴权模型（安全设计亮点）

- 请求头：`X-Cache-Caller` / `X-Cache-Timestamp` / `X-Cache-Sign`。
- 签名算法：`HMAC-SHA256(secret, caller + "\n" + timestamp + "\n" + METHOD + "\n" + path)`（CacheAuthSignUtil，**不覆盖 body/query 值**）。
- 校验链：三头齐全 → 时间戳漂移窗口（maxTimeSkewSeconds，默认 300s）→ 调用方 secret 存在 → 签名 `MessageDigest.isEqual` 恒时比较 → 按路径+方法解析权限（READ/WRITE/KEYS/TEST/ADMIN）→ 调用方权限白名单。
- 权限判定：`/test/`→TEST（可关闭）；`/cache/keys`、`/v2/cache/keys`→KEYS；GET→READ；其余→WRITE。
- 调用方（webmaster 等）通过 Feign 拦截器自动附加签名头（CacheFeignAuthConfig）。

## 7. 核心业务链路详解

### 7.1 外部发送链路（POST /sms/single_send）

1. **参数校验**：`SingleSendForm` 使用 `@Validated`（BindingResult 首错返回）。
2. **基础校验链**（`CheckFilterContext`，顺序来自 Nacos `filters` 配置，**默认 `apikey,ip,sign,template`**）：
   - `ApiKeyCheckFilter`：apikey 有效性（查缓存 client_business），回填 clientId
   - `IPCheckFilter`：IP 白名单（**白名单为空即放行**，fail-open）
   - `SignCheckFilter`：短信必须 `【...】` 开头，签名须在 client_sign 集合中
   - `TemplateCheckFilter`：去签名前缀后与 client_template 精确匹配（支持单 `#xx#` 占位符前后缀匹配）
   - `MobileCheckFilter`、`FeeCheckFilter`：**有实现但默认不在链中**（手机号格式校验、余额校验——只查不扣，SINGLE_FEE=50 厘/条，70 字/条计费），需在 Nacos 显式追加
   - 链序有隐式依赖：apikey → sign → template；配置错序会运行时 500
3. **组装 StandardSubmit** → `SnowFlake` 生成 sequenceId → `LocalDateTime.now()` sendTime。
4. **投递** `sms_pre_send_topic`（CorrelationData = sequenceId）。
5. **返回** `{uid, sid}`。

### 7.2 内部发送链路（POST /sms/internal/single_send）

供平台内部系统（webmaster 后台批量发送等）调用：
- `X-Internal-Token` 头与配置 `internal.sms.token` 比对（配置为空则不校验 —— 见风险节）。
- 通过 `client_business:{apikey}` hash 的 `id` 字段解析 clientId。
- 不走公开校验链，直接入队。

### 7.3 策略链（beacon-strategy）

`PreSendListener` 消费 `sms_pre_send_topic` → `StrategyFilterContext.strategy(submit)`：
- 从缓存读取客户策略链配置 `clientFilters`（`client_business:{apikey}` hash，逗号分隔，按配置顺序执行）；`black` 为向后兼容别名（展开为 blackGlobal+blackClient）。
- **fail-open**：`clientFilters` 为 null 时直接返回 → 消息被静默 ACK 丢弃（不路由不报错）；未知过滤器名仅 warn 跳过。
- 过滤器实现（`@Service(value=...)`，共 10 个）：
  - `blackGlobal` / `blackClient`：全局/客户黑名单（拦截，回传失败）
  - `dirtyword`（IK 分词 + sinter）/ `dfaDirtyWord`（自研 DFA）：命中**只 log 不拦截**（形同虚设）；`hutoolDFADirtyWord`：**唯一真正拦截**的敏感词实现；DFA 树类加载时一次性构建（**更新敏感词需重启**）
  - `limitOneHour`：仅验证码类，分钟/小时/天三级 zset 计数限流（zadd/zcount/zremove 三次 HTTP 非原子；zadd 返回 false=同毫秒重复被误判为限流命中）
  - `fee`：Feign 调 webmaster `/internal/balance/debit` **先扣费后路由、无退费补偿**；透支额度硬编码 -10000 厘
  - `phase`：号段补齐（Redis `phase:{前7位}`，未命中同步调 360 接口，RestTemplate 无超时）；`substring(0,7)` 遇短号抛越界 → 未 ack 重投
  - `transfer`：携号转网纠正运营商（Redis `transfer:{mobile}`）
  - `route`：通道路由（见下）
- **webmaster 新建客户默认链 `blackGlobal,blackClient,dirtyword,route`**：不含 fee/phase/transfer/limitOneHour → 新客户默认不扣费、不补运营商、不限流，且敏感词选中的是无拦截效果的 dirtyword。
- 顺序约束（代码不强制）：phase/transfer 须在 route 前；fee 须在 route 前；route 必须最后。
- **路由逻辑（RouteStrategyFilter）**：
  1. 取客户通道绑定列表，按 `weight` 降序 + channelId 升序排序（无流量负载均衡，纯静态权重）；
  2. 过滤：绑定可用（`isAvailable==0` 视为可用，语义倒置）&& 通道可用 && 通道支持该运营商（channelType==0 通用）；
  3. 取第一个命中 → 设 channelId、`srcNumber = channelNumber + clientChannelNumber`（纯字符串拼接）；
  4. **每条消息都 `declareQueue(durable(sms_gateway_topic_{channelId}))`** 后直投（多一次 broker 往返）；
  5. 无可用通道 → 写日志 + 推送失败报告 + 抛 StrategyException（消息被 ACK 丢弃）。
- **拦截旁路**（ErrorSendMsgUtil）：拦截时 `sendWriteLog`（reportState=2 写 ES）+ `sendPushReport`（客户回执，Redis SETNX 24h 去重）——失败闭环，但去重仅 24h。
- **性能**：所有 Redis 访问经 Feign HTTP 走 beacon-cache，单条消息约 **7~12 次 RPC**；PreSendListener 单线程消费（无 concurrency 配置）；Feign/RestTemplate 无超时，cache 服务抖动=策略全链路中断。

### 7.4 网关下发（beacon-smsgateway，CMPP 2.0 over Netty）

1. `SmsGatewayListener` 消费 `sms_gateway_topic_{channelId}`：
   - `MsgUtils.getSequence()` 生成 CMPP 序列号（static synchronized 自增，超 MAX/2 重置为当前毫秒；多实例会重叠）；
   - 构造 `CmppSubmit`（CMPP2_VERSION）；
   - **将 submit 以 JSON 暂存到 beacon-cache**（`cmpp:submit:{seq}`，TTL 600s）—— 进程重启也不丢关联上下文；
   - `nettyClient.submit(cmppSubmit)` —— **忽略返回值**：连接断开时返回 false，消息仍被 ACK → 短信静默丢失（无重试无补偿）。
2. **Netty 客户端**（NettyStartCMPP → NettyClient，参数硬编码 host=127.0.0.1, port=7890, serviceId=cz, pwd=123）：
   - `@Bean(initMethod="start")` 启动时同步 `connect().sync()` —— CMPP 服务不可达时**应用启动失败**；
   - 每次 `doConnect` 新建 `NioEventLoopGroup(4)` 且从不 shutdown（**重连线程泄漏**）；`bootstrap.handler` 调用两次，LoggingHandler 被覆盖；
   - `channelInactive` 在 Netty I/O 线程上同步阻塞重连（connect+10s sleep）→ 阻塞该 EventLoop；
   - 心跳：`IdleStateHandler(0,0,20)` 只监控 ALL_IDLE 且**不校验 ActiveTest 应答**，半开连接无法及时发现。
3. **第一次响应（CmppSubmitResp）**：`CMPPHandler` 交给线程池 `cmppSubmitPool` → `SubmitRepoRunnable`：
   - 按 sequenceId 从缓存原子取回 submit（`cmpp:submit:{seq}`），取不到则告警丢弃；
   - result==0（成功）：submit 拷贝为 StandardReport 并暂存 `cmpp:deliver:{msgId}`（等最终回执关联）；
   - result!=0（运营商拒绝）：submit 标记 `reportState=2` + errorMsg（CMPP2ResultEnums 映射）；
   - 两种情况都把 submit 发往 `sms_write_log_topic`（搜索模块写发送日志）。
4. **第二次响应（CmppDeliver 状态报告，registered_delivery==1）**：`cmppDeliverPool` → `DeliverRunnable`：
   - 按 msgId 取回 report；`stat=="DELIVRD"` → 成功，否则失败 + 错误描述（CMPP2DeliverEnums）；
   - 客户开启回调（isCallback）且有 callbackUrl → 发 `sms_push_report_topic`；
   - 发 `sms_gateway_normal_exchange`（TTL 延迟 10s → 死信 → 搜索模块更新 ES 状态）。
5. 用户上行（registered_delivery==0）：仅打印日志，不处理。
6. **CMPP 报文要点**（netty4/entity/）：消息头 = totalLength(4B)+commandId(4B)+sequenceId(4B)；`CmppSubmit`：version 2.0/3.0 双支持、`srcId = 源号码 + "1630"`（硬编码后缀）、msgFmt=8（UCS2，内容按 UTF-16BE 编码）、registeredDelivery=1（要状态报告）、destTerminalId 定长 21 字节；编解码由 `CMPPEncoder`/`CMPPDecoder`（LengthFieldBasedFrameDecoder）负责，支持 byte/int/long/String(UTF-16BE)/CmppMessageHeader 多类型写出。
7. 线程池：`ThreadPoolConfig`（hippo4j 动态线程池，bean 名 `cmppSubmitPool` / `cmppDeliverPool`，通过 SpringUtil 获取）。

### 7.5 日志写入（beacon-search）

`SmsWriteLogListener` 消费 `sms_write_log_topic`：StandardSubmit 转 Map，sendTime 转 epoch millis，`index(sms_submit_log_{当前年}, docId=sequenceId)` 写入 ES。**幂等缺陷**：`index` 要求返回 created，消息重投返回 updated 即抛 SearchException → 未 ack → **无限 requeue（重试风暴）**。

### 7.6 状态更新（beacon-search，死信延迟链）

网关发 `sms_gateway_normal_exchange`（fanout）→ normal_queue（TTL 10s，DLX=dead_exchange，**无消费者**）→ 过期进 `sms_gateway_dead_queue` → `SmsUpdateLogListener`：把 report 放 `ThreadLocal`（SearchUtils）→ `searchService.update(索引, sequenceId, {reportState})`。

- **只更新 reportState**，errorMsg 不入 ES（最终失败原因查不到）。
- 文档不存在且 reUpdate=false → 置 reUpdate=true 重新投回 normal 队列（再延迟 10s 重试一次）；第二次仍不存在 → 丢弃。
- 更新成功判定 UPDATED||NOOP；异常则不 ack → requeue（ES 故障时可能无限重试）。
- 索引取"当前年"，**跨年边界（12/31→1/1）回执会更新到新年索引** → 文档不存在 → 重试一次后丢失。

### 7.7 客户回调（beacon-push）

`PushReportListener` 消费 `sms_push_report_topic`：
- 无 callbackUrl → 直接 ACK 放弃；
- `RestTemplate.postForObject("http://" + callbackUrl, JSON(report))`，响应体必须等于 `"SUCCESS"`；
- 失败 → resendCount+1（>=5 放弃），投递 `push_delayed_exchange`（x-delayed-message fanout，延迟 0/15s/30s/60s/300s）→ `delayedConsume` 再次处理。
- **隐患**：RestTemplate **无 connect/read 超时**（坏地址永久阻塞消费者线程，默认单线程并发 → 队头阻塞）；重试 5 次后**静默丢弃**（无死信无告警）；delayed 交换机**非 durable**；callbackUrl 由客户配置（`client_business:{apiKey}` hash）→ **SSRF 面**，且强制 http（不支持 https）。

### 7.8 监控（beacon-monitor，XXL-Job）

- `monitorQueueMessageCountTask`：`cacheClient.keys("channel:*")` 拿通道号 → 检查 `sms_pre_send_topic` 与各 `sms_gateway_topic_{id}` 积压 > 10000 → 邮件告警（spring.mail.username/tos）。
- `monitorClientBalanceTask`：客户余额巡检（详见模块报告）。

### 8.4 beacon-strategy（38 类）

- 入口：`StrategyStarterApp`（@EnableFeignClients；手动注册裸 RestTemplate，无超时）、`PreSendListener`（仅 catch StrategyException，其它异常未 ack 依赖 broker 重投）

- 客户端：`BeaconCacheClient`（Feign 全部 Redis 访问）、`InternalBalanceClient`（扣费）、`CacheFeignAuthConfig`（签名头）
- MQ：声明 4 个 durable 队列（pre_send/mobile_area_operator/write_log/push_report），全部 default exchange 直投

### 8.5 beacon-smsgateway（28 类）

- Netty CMPP 客户端：`NettyStartCMPP`（**硬编码连接参数**，initMethod 启动即连）、`NettyClient`、`NettyClientInitializer`（LengthFieldBasedFrameDecoder 无帧长上限 + IdleState ALL_IDLE 20s）、`CMPPEncoder`/`CMPPDecoder`（CONNECT_RESP 不校验 result；Deliver **从不回 Deliver_Resp**）、`CMPPHandler`、`HeartHandler`（I/O 线程阻塞重连）
- 报文实体：`CmppMessageHeader`（totalLength+commandId+sequenceId）、`CmppConnect`（版本字节硬编码 1）、`CmppSubmit`（**序列化缺 Msg_Fmt、TP_udhi 被写 8、Msg_Id 恒 0、msgLength 1 字节溢出、无长短信拆分、srcId 硬编码 +"1630"**）、`CmppSubmitResp`（msgId 取绝对值丢错误语义）、`CmppDeliver`（重叠左移拷贝、回执按 Msg_Fmt 选字符集）、`CmppActiveTest(Resp)`（应答 sequenceId 恒 0）
- 工具：`Command`（完整 CMPP 命令字）、`MsgUtils`（**时间戳用 12 小时制 hh**、鉴权 MD5、定长字节工具）
- 业务：`SmsGatewayListener`（**忽略 submit() 返回值**）、`SubmitRepoRunnable`（SubmitResp 直接失败**不触发客户回调**）、`DeliverRunnable`（cache Feign 异常时状态更新/推送被跳过且异常静默）、`CmppStateStore`（Redis 暂存，无超时兜底 → 无回执的短信永久 waiting）
- 线程池：`ThreadPoolConfig`（hippo4j @DynamicThreadPool cmpp-submit/cmpp-deliver，**未显式配置容量/拒绝策略**；池满 RejectedExecutionException 沿 Netty 传播可关闭通道）
- 另有 `TestController`（遗留调试端点，直连生产线程池）

### 8.6 beacon-search（12 类）

- `RestHighLevelClientConfig`（ES 7.6.2 客户端，无超时/连接池配置；host:port 逗号分隔解析，不支持 IPv6）
- **无显式索引 mapping**（全靠 ES 动态映射），索引 `sms_submit_log_{年}`，文档 id=sequenceId
- 监听器：`SmsWriteLogListener`（写日志；**index 幂等判定错误——要求 created，重投返回 updated 即抛异常 → 无限 requeue 重试风暴**）、`SmsUpdateLogListener`（消费死信队列只更新 reportState，ThreadLocal 传上下文且成功路径不清理）

- 接口：`SmsSearchController`（`POST /search/sms/list`、`POST /search/sms/countSmsState`）——**无认证/授权/租户隔离，不传 clientID 可查全量客户手机号与内容**；countSmsState 用 size(0)+terms 聚合绕过 10000 限制
- 声明 normal/dead TTL 死信链（与网关重复声明）

### 8.7 beacon-push（5 类）

- `PushReportListener`（consume + delayedConsume 共用 process；失败也 ACK、靠重发重试；5 次后静默丢弃）
- `RabbitMQConfig`（`push_delayed_exchange`：x-delayed-message + x-delayed-type=fanout，**非 durable**；`push_delayed_queue` durable）
- `RestTemplateConfig`（**纯 new RestTemplate()，无超时无连接池**）
- 重试：延迟序列 0/15s/30s/60s/300s；成功判定 = 响应体精确等于 `"SUCCESS"`；callbackUrl 客户配置 → SSRF 面；5 个单测覆盖重试路径

### 8.8 beacon-monitor（11 类）

- XXL-Job 2.3.1：`XxlJobConfig` + `XxlJobProperties`（启动校验），3 个任务：`monitorQueueMessageCountTask`、`monitorClientBalanceTask`、`test`

- 调度 cron 与 `xxl.job.*` 配置均不在仓库，依赖 Nacos `beacon-monitor-dev.yml`

### 8.9 beacon-webmaster（198 类，纯 REST 运营后台）

- 控制器（27 个，接口全清单见 analysis/report_webmaster.md）：系统管理、客户/通道/绑定、模板/敏感词/黑名单/号段/携转/限流、策略链编排、代发短信（批上限 500，逐条调 api 内部接口）、检索透传（非 root 强制限定 clientID）、ECharts 统计、Quartz 定时任务管理（DB 配置 bean/method 反射执行）、余额充值（GET /pay）、缓存重建、内部扣费（/internal/balance/debit）

## 11. 已知问题与风险

> 完整清单以各子代理报告为准，此处汇总关键项。风险等级标注：🔴高危 🟡中危 🟢低危。

**🔴 认证与授权（webmaster）**
1. **服务端授权完全缺失**：`ShiroRealm.doGetAuthorizationInfo` 返回 null（ShiroRealm.java:60-62），任意登录用户可调用全部管理接口（增删用户、分配菜单、充值、缓存重建、定时任务）。
2. **内部扣费接口匿名**：`/internal/balance/debit` 在 Shiro 链为 anon 且 `internal.balance.token` 默认空=不校验（ShiroConfig.java:55、application.yml:47-48）——默认配置下任何人可调扣费接口。
3. **JWT 密钥硬编码** `"beacon-webmaster-secret-key-2026"`（JwtUtil.java:18），可伪造任意用户 token。
4. **权限判定用角色名字符串** `"管理员"`（WebMasterConstants.ROOT）——改名即失效/可提权。
5. **万能验证码 1111** + 验证码存无 TTL 内存 Map + 默认密码 123456 + 改密接口空壳（SmsUserController.java:122-126）。
6. **敏感信息泄露面**：`/sys/user/list` 返回密码哈希（SysUserConverter.java:44）；channel 密码明文存储并回传；CORS 反射 Origin 允许任意跨域携带 Authorization。

**🔴 主链路可靠性**
7. **策略链 fail-open + 顺序无约束**：`clientFilters` 缺失时消息**静默 ACK 丢弃**（StrategyFilterContext:32-34）；链顺序依赖运营配置（fee/phase/transfer 必须在 route 前），配错即漏扣费/错误路由。
8. **默认链缺核心过滤器**：webmaster 新建客户默认 `blackGlobal,blackClient,dirtyword,route`（ClientBusinessServiceImpl:133）——不含 fee/phase/transfer/limitOneHour，新客户不扣费、不补运营商、不限流；且敏感词选中的 `dirtyword` **只 log 不拦截**（形同虚设，dfaDirtyWord 同样如此，仅 hutoolDFADirtyWord 真正拦截）。
9. **扣费无闭环**：fee 过滤器先扣费（Feign 调 webmaster）后路由，route 失败（无通道）**不退费**；透支额度硬编码 -10000L；扣费路径与缓存域契约「MySQL 原子更新」约定存在实现漂移。
10. **限流误杀 + 非原子**：zadd 返回 false（同毫秒重复）被误判为命中拒绝；zadd/zcount/zremove 三次独立 HTTP 非原子，并发可穿透；阈值/窗口/时区全部硬编码。
11. **策略拒绝即 ACK 丢弃**：`PreSendListener` 对 StrategyException 手动 ACK；而其它 RuntimeException（NPE、Feign 异常、substring 越界）未 ack → 确定性异常**无限重投**。
12. **敏感词树不更新**：DFAUtil/HutoolDFAUtil 静态块类加载时一次性建树，运营增删敏感词不重启不生效；IK 分词异常路径有 NPE 隐患。
13. **ES 索引按“当前年”路由**：写入/更新都取服务器当前年，跨年边界（12/31↔1/1）消息写错索引、回执更新到新年索引 → 重试一次后状态丢失；更新链路依赖 `ThreadLocal` 传上下文（成功路径不清理，泄漏隐患）。
14. **CMPP 序列号回绕冲突**：`MsgUtils.getSequence()` 自增回绕 + Redis `cmpp:submit:{seq}` 键复用（TTL 600s 缓解，高并发下仍有理论碰撞面）。
15. **网关连接参数硬编码**（NettyStartCMPP：127.0.0.1:7890/cz/123），多通道扩展受限。
16. **缓存全走 Feign HTTP**：策略单条消息约 7~12 次 RPC（无本地缓存/无批量），Feign/RestTemplate 无超时——cache 服务抖动即全链路中断；confirm/return 回调只 log 无补偿，投递失败静默丢失。
17. **CMPP 协议实现缺陷**（与真实运营商对接前必须修复）：CmppSubmit 序列化缺 Msg_Fmt 字段、TP_udhi 位置写入 8（字段整体错位 1 字节）、Msg_Id 恒 0（所有回执关联键退化为 "0"）、msgLength 1 字节（>255 字节溢出）、鉴权时间戳用 12 小时制 hh（下午时段不符合协议）、Connect 版本字节硬编码 1、CONNECT_RESP 不校验 result、收到 Deliver 从不回 Deliver_Resp（ISMG 会重发）。
18. **网关断连静默丢短信**：`SmsGatewayListener` 忽略 `submit()` 返回值，连接断开时消息仍被 ACK（SmsGatewayListener.java:48,58）；SubmitResp 未到则 600s 后缓存过期，短信永久停留在 waiting 状态（无超时兜底任务）。
19. **网关连接管理缺陷**：每次重连新建 NioEventLoopGroup(4) 从不关闭（线程泄漏，每轮断线最多 40 线程）；channelInactive 在 Netty I/O 线程上同步阻塞重连；半开连接无法及时发现（心跳不校验应答）；DeliverRunnable 中 cache Feign 异常时最终状态既不更新也不推送（异常静默消失）。
20. **ES 幂等判定错误 → 重试风暴**：`index` 要求返回 created，重投返回 updated 即抛异常 → 手动 ack 模式无限 requeue，阻塞队列头（ElasticsearchServiceImpl.java:74-79）。
21. **检索接口无租户隔离**：`/search/sms/list`、`/search/sms/countSmsState` 无认证/授权，不传 clientID 可查询全部客户的手机号、短信内容、apiKey（SmsSearchController.java:23-35）；from/size 无上限。
22. **回调推送可靠性缺口**：RestTemplate 无超时（坏地址阻塞消费线程，队头阻塞）；重试 5 次后静默丢弃（无死信无告警）；callbackUrl 客户配置 → SSRF；SubmitResp 直接失败不触发客户回调（客户收不到失败通知）；ES 只更新 reportState，errorMsg 不入库。

**🟡 安全与配置**
23. **缓存签名不覆盖 body/query 且无 nonce**：X-Cache-Sign 只覆盖 caller+timestamp+method+path，写接口的 body/query 值可被篡改而不破坏验签；300s 时间窗内可重放（CacheAuthSignUtil.java:27-33）。
24. **Redis 多态反序列化风险**：beacon-cache RedisConfig `enableDefaultTyping(NON_FINAL)`（RedisConfig.java:51），JSON 反序列化信任类名，属历史 CVE 高发模式。
25. **内部接口鉴权普遍默认关闭**：`internal.sms.token`（api）与 `internal.balance.token`（strategy/webmaster）默认空串=不校验；api 内部接口还跳过全部业务过滤器；IP 白名单为空即放行（fail-open）；x-forwarded-for 可取首值伪造。
26. **凭据大面积明文入库**：cache 各 caller 的 HMAC 密钥、monitor 的 QQ 邮箱+SMTP 授权码+收件人、webmaster 的 DB root/123、JWT 密钥，全部硬编码提交仓库。
27. **监控任务缺陷**：每次调度创建的 RabbitMQ Connection/Channel 从不 close（资源泄漏）；余额任务 `Long.parseLong(map.get("balance")+"")` 遇脏数据 NPE/NumberFormatException 致整个任务失败；低余额客户**每次调度重复收邮件**（无节流）；queueDeclare 作为读数量前置有副作用；channelId 提取靠 `key.substring(8)` 字符串切片。
28. **反射执行任意 Bean 方法**：schedule_job 表可配置 bean_name/method_name 反射调用（ScheduleInvokeServiceImpl.java:60-86），结合授权缺失可执行任意方法。
29. **遗留调试端点**：smsgateway `/test` 直连生产线程池执行任务（TestController.java:21-27）。

**🟡 数据一致性**
30. **内存假存储**：AcountServiceImpl（充值流水）与 LegacyCrudServiceImpl（activity/apimapping/grayrelease/publicparams/notify/searchparams/clientsign/clienttemplate 等 8 域）用 ConcurrentHashMap 存数据，重启即丢，与 DB 真实表脱节。
31. **客户归属用 client_business.extend1** 存运营用户 id，无索引、建模不规范；多 list 接口全表查出后内存 subList 分页。
32. **缓存同步默认关闭**（sync.enabled: false），与 docs 描述的三层同步闭环不一致。
33. **GET 请求做充值**（/sys/client-business/pay）。

**🟢 工程问题**
34. **监控队列名 pattern 依赖**：`channel:*` Redis 键与 `sms_gateway_topic_{id}` 拼接约定耦合，数据不一致时漏检。
35. **多模块拓扑声明分散**：无单一事实源；normal/dead TTL 死信链在 beacon-search 与 beacon-smsgateway **两份相同声明**（参数一旦不一致，启动即 406 前置条件失败）；`*_topic` 常量实为队列名（default exchange 直投），与 `*_exchange/queue` 两套风格并存。
36. **文档漂移**：docs/01 仍列 `beacon-test` 模块（当前根 POM 已无）；README 已更新为 9 模块。
37. **死代码/杂质**：`CMPPSubmitRepoMapUtil`/`CMPPDeliverMapUtil`（Caffeine）已无调用方（网关改用 Redis 版 CmppStateStore）；`ChannelTransferUtil` 空实现、`oneHourLimitMilli` 死字段、DFAUtil 残留 main、PhaseStrategyFilter 大段注释旧实现；EncDecodeUCS2 未被 netty4 链路使用。
38. SQL 注入风险低：全部 `#{}` 绑定；`${}` 仅 MyBatis Generator 内部 criterion/orderByClause（业务硬编码），暂无注入点。

## 12. 设计亮点（值得保留）

1. **配置驱动的过滤器链**：API 校验链（Nacos `filters`）与策略链（Redis `clientFilters`）均可在线调整，且 API 侧启动期校验链名合法（未知过滤器启动即失败）。
2. **缓存域契约体系**（beacon-common `cache` 包）：9 个缓存域统一声明 key 模板、Redis 类型、真源（MYSQL）、写入/删除/重建策略、归属服务（CacheDomainRegistry）——为「MySQL 真源 + Redis 派生」的同步/重建链路提供元数据，余额域用 `OVERWRITE_ONLY + MYSQL_ATOMIC_UPDATE_THEN_REFRESH` 表达高风险语义。
3. **beacon-cache 鉴权设计分层清晰**：caller→secret、caller→permission 分离；恒时比较验签；时间窗防重放（300s）；权限模型 READ/WRITE/KEYS/TEST/ADMIN；keys 扫描白名单防任意遍历；逻辑 key/物理 key 命名空间隔离。
4. **原子操作封装**：锁申请（setIfAbsent+TTL）、CAS 锁释放（deleteIfValueMatches）、消费即删（getAndDelete）均用 Redis 原子命令/Lua 实现；类型化读接口用 BigDecimal exact 转换防精度截断。
5. **失败旁路闭环**：策略拦截不静默——统一写 ES 日志（reportState=2）+ 推送客户回执（SETNX 去重），配合「业务异常也 ACK」避免队列堆积。
6. **网关 CMPP 中间状态外置 Redis**（CmppStateStore，TTL 600s/86400s）：提交-应答、应答-回执两段关联不依赖进程内存，重启不丢关联（相对 beacon-common 遗留 Caffeine 方案是改进）。
7. **回执回调延迟重试**：x-delayed-message 交换机实现 0/15s/30s/60s/300s 指数退避，最多 5 次，且 24h 去重。
8. **雪花 ID 防护**：synchronized、时钟回拨直接失败、强制正数。
9. **测试覆盖**：strategy/common/search/push 共 34+ 单测覆盖核心路径（PreSendListener ack 语义、链展开、路由、限流、ES 幂等/查询构建/时间兼容、推送重试延迟/上限/序列化失败）。
10. **回执幂等吸收**：`cmpp:deliver:{msgId}` 的「pop 取走」原子语义吸收重复 Deliver；`countSmsState` 用 size(0)+terms 聚合绕过 ES 10000 条分页上限；网关监听队列提前声明避免监听容器启动反复重试。
